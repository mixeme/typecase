# Библиотека печатает макет

Инструкция исполнителю. Развилок нет: все решения закрыты человеком и записаны в разделе «Решения». Исключение одно — список виджетов без кадра шага 7 (Р-15) человек подтверждает, когда он собран. Чекбоксы отмечают по мере коммитов.

Второй из трёх планов. Первый — «Макет — единственный источник вида» — закрыт выпуском 0.6.0; его правила и решения живут в [docs/visual/mockup.md](../visual/mockup.md), его хвосты закрыты 2026-09-26. Итог первого плана: макет на словаре `tc-*`, CSS продукта одним блоком `<style data-tc>`, в кадрах настоящие элементы, дизайнерских `style=` нет. Третий — [3-screens-and-checks.md](3-screens-and-checks.md).

Макет независим от Typecase (Р-1): библиотека читает его копию `docs/visual/carrel-ui-mockups.html`, макет о библиотеке не знает.

**Цель.** Экран, собранный из виджетов, совпадает с макетом сам. Это держится на трёх вещах, и все три проверяются кодом:

1. **CSS один.** CSS библиотеки — дословный вырез блока `data-tc` из копии макета. Ворота сверяют, что вырез и файл библиотеки совпадают байт в байт.
2. **Виджет печатает фрагмент своего кадра.** У каждого виджета есть эталон — место в кадре макета; тест сверяет дерево `Render` с деревом фрагмента: теги, классы, текст.
3. **Контейнер принимает только то, что макет в него кладёт.** Допустимые вложения выведены из кадров и закреплены типами Go: неправильное вложение не компилируется.

Одинаковый CSS и одинаковое дерево дают одинаковую картинку, поэтому сверка виджета статическая, без браузера. Браузер нужен только там, где вид зависит от поведения: `tc.js`, замеры, фокус — план 3.

Что остаётся на совести экрана — какие виджеты и в каком порядке. Это ловит сверка экрана с его кадром в плане 3.

## Почему так

Два плана раскладки кончились одинаково: ворота зелёные, экраны кривые. Причина общая — между макетом и библиотекой стоял перевод (числа в таблицах `layout`, прозу анатомии в спеке, композицию экранов на глаз), и проверялось то, что легко проверить, а не то, что видно. Пруфы (`internal/proof`, страница `/compare`) показали обратное: когда виджет печатает разметку кадра, а CSS взят из макета, шесть кадров на пяти ширинах сходятся с нулём расхождений, и каждое найденное расхождение — описка макета или решение, которое никто не принял.

План 1 убирает перевод со стороны макета. Этот план — со стороны библиотеки.

## Судьба пакета `layout`

Вопрос был: пригодится ли слой, который вобрал бы логику сужения экрана.

Логика сужения — действительно самая трудная часть, и ей нужен один дом. Но таблицы чисел в Go этим домом быть не могут: сужение — дизайнерское решение, его рисуют и смотрят в макете. Если оно живёт в Go, кто-то снова переводит нарисованное в таблицы — это третья копия, из-за которой не сошлись прошлые планы. В макете сужение уже выражено CSS (`docs/visual/mockup.md`, «Узкие экраны»): именованные контейнеры `tcbox`, правила компонентов на лестнице ширин, состояния оболочки (Р-3) как свойство `--tc-shell-mode`, которое читает `tc.js`. Страховка от переполнения баров (Р-4) — единственное, что библиотека добавляет сверх макета, и она не действует на содержимом макета.

Из `layout` переживают план **идеи**, а не код:

| Что было в `layout` | Где теперь |
|---|---|
| Числа дорожек, высот, отступов | CSS макета |
| `@container` для узких раскладок | CSS макета, лестница ширин на странице макета |
| Одно имя контейнера `tcbox` | правило линта макета `named-container` (`docs/visual/mockup.md`, «Проверки») |
| Имена слотов вместо `:nth-child` | классы `tc-*__…` в макете и в `Render` |
| `slots == tracks`, «сетка только в списке» | сверка фрагмента (шаг 2) и типы контейнеров (шаг 3) |
| Паритет таблиц с макетом | ворота `css-from-mockup`: CSS — вырез из макета |
| Инвентарь `.m-*` | не нужен: `m-*` нет (линт макета) |
| Look на четырёх ширинах | лестница ширин (`docs/visual/mockup.md`, «Узкие экраны»): экраны на десяти ступенях против кадров — план 3 |

Порог узкой оболочки сейчас записан дважды: 1190 в CSS, 640 в `tc.js`. После плана — один раз, в CSS; `tc.js` читает режим, а не держит число.

## Решения

Нумерация общая для трёх планов. Все закрыты человеком.

- **Р-2.** Пакет `layout` удаляется: таблицы, генерация, инвентарь, паритет. Сужение живёт в CSS макета и состояниях оболочки; идеи переносятся по таблице выше.
- **Р-5.** Один ломающий выпуск **0.7.0** (0.6.0 занят выпуском плана раскладки и макета-источника). Никаких миграций, переходных слоёв и legacy: старые виджеты, CSS и ворота удаляются целиком, руководства по переходу нет. Работа на ветке, `main` не трогается до слияния.
- **Р-18. Данные — цвет коллекции, доля полосы.** Carrel отдаёт CSP без `unsafe-inline` для скриптов и стилей и запрещает `style=` целиком: «цвет — атрибутом, который она читает» (C-11 спеки Carrel). Виджет печатает `data-tc-colour`, `data-tc-width` — как кадр макета; `tc.js` ставит `--tc-colour`, `--tc-width` через CSSOM (CSP это разрешает); CSS читает `var(--tc-colour)`. Разметка кадра и виджета совпадает буквально.
- **Р-19. Typecase остаётся библиотекой общего назначения.** Макет — её визуальный источник; содержимое кадров — примеры. Правило «имена по роли, без доменных слов» (L-2.2) остаётся. Спека ссылается на макет как на эталон вида и больше ни на что.
- **Р-20. Вырез CSS лежит в репозитории файлом** `css/typecase.css`. Запрет готовых файлов сборки (L-11.1) получает исключение: этот файл сверяют с макетом байт в байт ворота `css-from-mockup`, поэтому незаметно разойтись он не может.
- **Р-21. Зона нажатия в узком состоянии — 44 px** (L-9.2 без изменений; проверка `tap-target` остаётся). Рисунок не растёт — расширяется зона (`docs/visual/mockup.md`, Р-21).
- **Р-15** — ниже; список человеку на шаге 7.

**Р-15. Виджеты каталога, которых нет в инвентаре макета.** Сейчас это `tc-chip`, `tc-cols`, `tc-crop`, `tc-docedit`, `tc-pfield`, `tc-pfieldrow`, `tc-pick`, `tc-rail`, `tc-row--avatar`, `tc-row--lead`, `tc-row--meta`, `tc-row--tick`. Часть есть в макете под другим именем (`tc-rail` — `m-rail`, `tc-crop` — кадр «Фотография контакта · кадрирование», `tc-pick` — `m-in.is-pick`, `tc-docedit` — «Заметка · правка на весь экран»), часть — дубли (`tc-pfield` при `tc-field`, `tc-chip` при `tc-tag`), `tc-cols` уже стал компонентом раскладки макета (`docs/visual/mockup.md`, «Клей раскладки»). Решение: сопоставить найденное, дубли удалить, по остальным — список человеку на шаге 7: нарисовать в макете или удалить. Виджет без кадра не остаётся.

## Закрытые решения

| Решение | Почему |
|---|---|
| Эталон виджета — запись `Ref{Frame, Class, N}`: `data-frame` кадра, класс блока, номер вхождения в кадре | Адрес без селекторного движка; кадр находится по номеру, не по подписи |
| Фикстура эталона — данные из кадра, руками, как в `internal/proof/screens*.go` | Сверка честная, только если данные те же |
| Нормализация дерева: тег; классы, отсортированные; текст со схлопнутыми пробелами (у `pre-wrap` — как есть); у `input` — `type`, `value`, `placeholder`; `data-tc-colour`, `data-tc-width`. Не сравниваются `aria-*`, `role`, `id`, `for`, значения `href`, `title` | Сравнивается то, что меняет картинку; доступность виджет добавляет сверх кадра |
| Парсер — `golang.org/x/net/html`, только во `internal` | Кадры — рукописный HTML с неявным закрытием; самодельный разбор ошибётся. L-11.1 в новой редакции (шаг 0): без сторонних зависимостей — код, который получает потребитель; проверки (`chromedp`, `x/net/html`) — во `internal` |
| Контейнер задаёт слоты интерфейсами с неэкспортируемым методом (`Block`, `Control`, `RailPart`, `SheetPart`…) | Неправильное вложение — ошибка компиляции, а не ворота после |
| `tc.js` и крючки `data-tc-*` — контракт; новая разметка несёт те же крючки | Поведение (ящик, меню, лист, фокус, дерево) уже проверено тестами |
| CSS контролов — в макете (`docs/visual/mockup.md`, «Закрытые решения»), не в библиотеке | Макет рисуется теми же элементами |
| Ни экран, ни виджет не печатают `style=` | Ворота `screens-css`, `no-inline` остаются; CSP Carrel (Р-18) |
| Шрифты библиотеки — свой `css/fonts.css` с `@font-face` на `fonts/`; блок `data-tc` шрифтов не объявляет | `@font-face` макета указывает на файлы рядом с макетом и живёт в `<style>` страницы |

## Шаг 4 — виджеты по семьям

Порядок семей: примитивы (кнопка, метка, тег, бейдж, флажок, клавиша, число) → поля и формы (поле, ввод, выбор, сегмент, флажок с подписью, набор полей, подвал формы) → строки и списки (варианты строки, строка источника, список, группа, дерево) → оболочка (корень, верхняя полоса, поиск, рейл, навигация, тело, `main`, панель, шапка, бар) → наложения (затемнение, лист, диалог, меню) → документ (текст, полоса правки, колонка сведений) → таблицы и карточки (таблица, имя файла, карточка, поля панели, секция, диагностика, сообщение, опасная зона, опрос, очередь, плитки) → состояния (пусто, скелет).

Для каждого виджета семьи:

- [ ] API — из фрагмента: поля структуры = переменные части кадра (текст, состояние `is-*`, вариант `--…`, дети по слотам). Имена Go — из имён CSS: блок `tc-tickrow` → тип `TickRow`; элемент `__title` → поле `Title`; варианты блока (`--…`) → одно поле-перечисление; состояния (`is-*`) → одно поле-перечисление, если они взаимоисключающие (механизм 3 спеки: `Open | Closed | Disabled`, не три `bool`); `bool` — только для независимого признака. Старые имена Typecase не сохраняются ради совместимости (Р-5).
- [ ] Спека L-4, семья: каждый виджет по формату L-3.2 (с «Эталоном»); старые описания семьи удалить.
- [ ] Эталоны: по записи на каждую форму блока из `shapes`.
- [ ] `TestWidgetFragments` по семье зелёный.
- [ ] Каталог: запись виджета — это его фрагмент; старые записи семьи удалить.

Семья закрыта, когда все её эталоны зелёные, в каталоге нет старых записей и L-4 семьи переписан.

Сделано так (начало шага 4):

- Старый пакет переехал целиком в `internal/legacy/widget`: им собраны демо-экраны, и сборка остаётся зелёной; удаляется на шаге 6 вместе с `layout`. Новый `widget` растёт с нуля по семьям.
- Каталог строится из таблицы эталонов: запись — клетка каталога в состоянии записи, внутри `tc-root`. Старых записей в каталоге нет с первой семьи.
- Спрайт библиотеки `icons/sprite.svg` — символы спрайта макета, вырезаются тем же `go generate ./css`, ворота `css-from-mockup` сверяют и его. `Icon` — имя символа без перечисления: набор значков — потребителя (L-5.1).
- Примеси контейнера: у каждого виджета неэкспортируемый `html(mix)`, `Render()` — то же без примесей; контейнер печатает на корне ребёнка `tc-push`, `is-2nd`, свой элемент.
- Варианты: независимые оси — отдельные поля (у `Dim` размер и посадка), совпадающие в кадрах вместе — одно значение перечисления (`MarkH11Inline`, `Mono11_5DustyGap`).
- Куски бегущего текста (`Text`, `Strong`, `Hint`, `Dot`) — не виджеты: у них нет своего блока и `Render`, они реализуют слоты текстовых блоков.
- Раздел L-4 семьи собирается из комментариев виджетов, чтобы описание в спеке и в коде не расходились. Ворота `widget-fragments` и `container-pairs` заведены сразу, на них опираются инварианты.
- Правка макета по ходу: `tc-stack__item` в подписи рейла стал `tc-dim__hint` (имя без правила, рисунок тот же); ползунок масштаба — `tc-field__zoom`; колонка меню весов — `tc-rubric__col`.
- Один блок — несколько типов, когда у блока разные элементы (`tc-in`: `Input`, `Pick`, `Filter`, `TagInput`, `Area`). Реестр ворот хранит описания по типу; привязки инвариантов — по типу или по блоку. Пары: рисованная пара разрешена, если хоть один тип ребёнка ложится в хоть один тип родителя.
- Положение (`Place`: прижат, тянется) и ранг (`Secondary`, is-2nd) — поля тех виджетов, у которых они встречаются: их выбирает автор экрана, как автор кадра. Элемент родителя на корне ребёнка (`tc-bar__more`) печатает контейнер.
- Части (`FieldHint`, `Swatches`, `Group`…) — куски виджета без своего блока и без `Render`; `refs.Parts` перечисляет их, проверка пар смотрит внутрь.
- Формы, чьи дети из будущих семей, или с дефектом кадра — в `refs.Waiting` с причиной; `TestShapesCovered` не пропускает форму без записи и без причины. Шаг 7 опустошает список.
