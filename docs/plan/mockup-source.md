# Макет — единственный источник вида

Инструкция исполнителю. Открытые решения собраны в разделе «Решения за человеком»; шаг, который от них зависит, не начинать, пока решение не закрыто. Остальное закрыто. Чекбоксы отмечают по мере коммитов.

Это первый из трёх планов. Второй — [library-from-mockup.md](library-from-mockup.md) (библиотека печатает макет), третий — [screens-and-checks.md](screens-and-checks.md) (экраны, проверки, переход). План библиотеки начинается, когда этот закрыт.

**Цель.** Макет пишется на словаре Typecase и становится тем, что библиотека берёт без перевода: один CSS на макет и продукт, классы `tc-*`, настоящие элементы в кадрах, ни одного `style=`. После плана кадр макета и экран продукта отличаются только тем, кто напечатал разметку: человек или `Render`.

## Почему так

Три пруфа (`internal/proof`, `internal/mockcss`, страница `/compare`) собрали шесть кадров из виджетов, которые печатают разметку кадра, с CSS, взятым из `<style>` макета. Заметки, файлы, тёмная тема, лист поверх экрана, подтверждение поверх настроек, настройки с открытым меню — на пяти ширинах (1351–700) расхождений ноль. Исключение одно — меню, которое макет рисует двумя способами (см. Р-7). Порча одного токена или одного правила ловится.

Всё, что в пруфе пришлось переводить, — это недостатки макета как источника, а не библиотеки:

| Что переводили | Сколько на 6 кадров | Во всём макете | Уходит на шаге |
|---|---|---|---|
| Префикс `m-` → `tc-`, словарь | таблица имён | 103 класса | 3 |
| Селекторы по тегу (`.m-seg span`, `.m-menu > div`) | 2 | см. шаг 3 | 3 |
| `span` вместо кнопок и полей | CSS контролов, 7 строк | все кадры | 4 |
| `style=""` в кадре → вариант виджета | 72 записи | 2597 атрибутов, 637 разных дизайнерских | 5 |
| Цвета меток в `style` | через `data-tc-colour` | 395 | 5 |
| Два способа открыть меню | 1 структурное расхождение | 4 меню из 6 внутри кнопки | 6 |
| `.mock.is-dark` вместо атрибута темы | подмена селектора | 1 кадр | 1 |

Префикс `m-` — от `.mock`, корня кадра; у макета не было задачи совпасть с библиотекой.

## Решения за человеком

Рядом с каждым — решение по умолчанию и почему. Исполнитель не выбирает сам. Нумерация общая для трёх планов: Р-2 и Р-5 — в плане библиотеки.

**Р-1. Где живёт общий CSS и чей макет.** По умолчанию: CSS лежит в Typecase и во время этого плана — в `docs/visual/css/`, в плане библиотеки переезжает в `css/`; макет подключает его `<link>`. Макет живёт в репозитории Typecase, копия в Carrel удаляется или становится ссылкой. Почему: один файл вместо двух копий, генератор не нужен. Цена: макет перестаёт быть одним самодостаточным файлом; для пересылки — сборка с вклеенным CSS (шаг 8).
*Иначе:* CSS остаётся в `<style>` макета, библиотека генерирует свой из него (как в пруфе, `internal/mockcss`). Работает, но держит генератор и правила выборки навсегда.

**Р-3. Планшетное состояние рейла.** Макет на ≤560 сжимает рейл до 56 px (значки), на телефоне — выдвижной рейл (кадр «Выдвижной рейл источников»). Typecase сейчас сразу переходит к ящику на ≤640 (`tc.js`), рейл 56 не делает. В схеме «макет — источник» сознательных расхождений нет: либо макет перерисовывается под ящик с 640, либо библиотека делает рейл 56. По умолчанию — ящик: он уже сделан и проверен; кадры 560 перерисовать.

**Р-4. Как бар отдаёт кнопки при сужении.** Макет: пороги CSS — элементы `is-2nd` прячутся на 800, «⋯» появляется через `:has()`. Typecase: `tc.js` меряет и переносит в «⋯» то, что не влезло (`data-tc-bar-overflow`, `top-overflow`, `seg-menu`, `crumbs-ellipsis`). По умолчанию: порядок отдачи задаёт разметка (`is-2nd` и дальше), момент — замер в `tc.js`; макет подключает `tc.js` и показывает то же, что продукт. Пороги CSS остаются только для колонок сетки (строки, таблицы). Почему: реальные подписи и переводы длиннее макетных, порог 800 их не знает.

**Р-6. Схема имён.** По умолчанию: `tc-блок`, `tc-блок__элемент`, `tc-блок--вариант`, состояния `is-*`; где инвентарь `layout/inventory.go` уже сопоставил класс с виджетом Typecase — брать имя Typecase (`m-bar3` → `tc-mark`, `m-src` → `tc-tickrow`, `m-f` → `tc-field`, `m-shell` → `tc-shell__body`); варианты строк — по форме, не по разделу (`m-row--note` → имя по составу колонок, как сейчас в Typecase). Почему: одна замена префикса оставит внутренние `.t .s .d .h .b .f .lbl .sep .mono` и селекторы по тегу — это ровно то, что в пруфе потребовало карт подмены.
*Иначе:* только префикс (`m-row .t` → `tc-row .t`). Быстрее на шаге 3, дороже на шаге 4 и в библиотеке.

**Мелкие, с решением по умолчанию** (список показать человеку одним сообщением, молчание = согласие):

## Закрытые решения

| Решение | Почему |
|---|---|
| В кадрах те же элементы, что печатает виджет: `button` у кнопки, варианта сегмента, флажка, пункта меню, выбора, крестика; `input`/`textarea` у поля; `a href` у ссылок; `kbd` у клавиши | Тогда дерево кадра и дерево виджета совпадают вместе с тегами, и сверка в библиотеке — статическая, без браузера |
| Меню — `.tc-drop`: кнопка и меню соседи | Меню не может быть содержимым `<button>` |
| `style=` в кадрах нет совсем | Иначе дизайнерское решение живёт в кадре, а не в CSS, и библиотеке нечего взять |
| Цвет коллекции — `data-tc-colour`, доля — `data-tc-width`; макет подключает `js/tc.js` | Механизм уже есть в Typecase; тот же в макете |
| Токены — `--tc-*` из `css/00-tokens.css` по именам; тёмная тема — `data-tc-theme="dark"` на корне кадра | Любой кадр можно показать тёмным одним атрибутом; значения тёмной темы в пруфе совпали до цвета |
| Шрифты — файлы Typecase (`fonts/`), моно — Source Code Pro | Макет рисуется тем же, чем продукт; сейчас на машине без Public Sans он рисуется Segoe/Georgia/Consolas |
| У каждого кадра стабильный `data-frame="…"` (латиница, `раздел-кадр`) | Маршрут демо и тест находят кадр по номеру, не по тексту подписи |
| Контейнеры — только именованные: `container: tcbox / inline-size`, `@container tcbox (…)` | Правило уже принято в Typecase (`typecase-layout.md`, «Контейнеры: одно имя») |
| Каждое правило CSS используется хотя бы одним кадром | Мёртвый CSS в макете — мёртвый CSS в продукте |
| Страница макета (оглавление, `.frame`, подписи, текст разделов) — своё оформление в `<style>` страницы, классы без `tc-` | Это не интерфейс продукта |

Нативный попап `input[type=date|time]` не заменять кастомным: внутри поля даты браузер рисует своё, коробка та же.

## Инструмент: снимок «до» и сверка

Шаги 1–5 не меняют вид. Проверять это глазами на 163 кадрах нельзя.

**Сверка.** Тест `internal/browser/mockup_refactor_test.go` (Chrome): берёт макет из git на базовом коммите (`git show <base>:docs/visual/carrel-ui-mockups.html` во временный каталог вместе с CSS того же коммита) и текущий; для каждого `data-frame` снимает кадр в обоих на ширинах **1351** и **820** и сравнивает попиксельно, допуск — сглаживание (канал ±2). Базовый коммит — конец шага 1: после него шрифты и токены те же, что в продукте, и дальше вид меняться не должен. Шаг 1 проверяется глазами на нескольких кадрах.

**Разрешённые изменения** — файл `docs/visual/allowed-diffs.md`: кадр, ширина, что меняется, какое решение (Р-7…Р-13). Сверка пропускает кадр только если он там записан. Поля даты и времени (шаг 4) — там же.

PNG в репозиторий не класть.

## Шаг 7 — узкие экраны

Здесь макет становится источником поведения при сужении, а не только широкого вида.

- [ ] Контейнеры: `tc-root`, `tc-main`, `tc-side`, `tc-list`, лист, диалог, колонка раскладки — `container: tcbox / inline-size`. Все `@container` — именованные.
- [ ] Лестница ширин на странице макета: переключатель над оглавлением ставит всем кадрам ширину 1351 / 1100 / 900 / 820 / 620 / 460 / 390. Это инструмент дизайна, не часть интерфейса продукта.
- [ ] Обход по лестнице: каждый компонент на каждой ступени. Где нет правила — дописать: поля формы в столбец, действия шапки переносом, карточка без внутренних колонок, лист на всю ширину с полями, `dl` полей в один столбец, таблица — по Р-4 и колонкам. Список дописанного — в отчёт шага.
- [ ] Оболочка: по Р-3. Режим оболочки (широкий / без панели / узкий) — пользовательское свойство на `tc-root` в `@container` (`--tc-shell-mode: narrow`), `tc.js` читает его, а не держит свой порог. Порог живёт в одном месте — в CSS макета.
- [ ] Телефонные кадры (7, `is-phone`): это те же кадры в узком режиме. Класс кадра `is-phone` уходит, телефонный вид даёт ширина 390 и режим оболочки. Кадр, у которого на телефоне другое содержимое, остаётся отдельным.
- [ ] Бары и шапка — по Р-4: у элементов порядок отдачи в разметке.

## Порядок

0 → 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8. Шаги 3 и 4 не менять местами: переименование сначала убирает селекторы по тегу, иначе смена тега ломает правила. Шаг 7 — после 5: узкие правила пишутся на чистых классах, а не на inline.

## Готово когда

- В макете нет `m-*`, `.mock`, `style=`; все классы — словарь `tc-*`, общий с библиотекой.
- CSS макета — файлы `docs/visual/css/`, которые план 2 переносит в `css/` без правок.
- Кадры собраны из тех же элементов, что печатают виджеты.
- Сверка «до/после»: отличия только из `allowed-diffs.md`, у каждого — решение человека.
- Лестница ширин показывает каждый кадр на семи ширинах, и у каждого компонента на каждой ступени есть правило.
- Решения Р-1, Р-3, Р-4, Р-6…Р-14 закрыты и записаны в этом файле.
