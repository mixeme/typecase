# Экраны, проверки, переход

Инструкция исполнителю. Развилок нет: все решения закрыты человеком и записаны в разделе «Решения». Исключение одно — список кадров вне экранов и компонентов шага 1 (Р-16) человек подтверждает, когда он собран. Чекбоксы отмечают по мере коммитов.

Третий из трёх планов. Шаг 1 делается на ветке плана 2 ([2-library-from-mockup.md](2-library-from-mockup.md)) до её слияния; остальное — после. Первый план закрыт; его правила — в [docs/visual/mockup.md](../visual/mockup.md), хвосты — в [1-mockup-tails.md](1-mockup-tails.md).

**Цель.** Демо-экран — это кадр макета, собранный виджетами; браузер сверяет его с кадром на лестнице ширин, и красное значит «не как в макете», а не «число не совпало с таблицей». Недостающее сначала рисуется в макете. Интерфейс Carrel начинается на 0.7.0. Пруфы убраны.

Макет независим от Typecase (Р-1): тесты читают его копию `docs/visual/carrel-ui-mockups.html`; правки макета делаются в самом макете, копия обновляется заменой файла.

## Почему так

Прошлые экраны демо собирались под ворота `screens-coverage` («каждый виджет каталога есть на каком-то экране»): дешевле всего было свалить виджеты раздела в одну колонку. Контакты несли десять кадров сразу, поиск 560×560 стоял посреди `main`, чипы и сегменты растягивались на всю колонку — при зелёных воротах. Look-тест мерил первый попавшийся узел каждого класса по списку чисел и этого не видел.

Здесь ворота устроены наоборот: маршрут = кадр, и сверяется весь кадр.

---

## Решения

Нумерация общая для трёх планов. Все закрыты человеком.

- **Р-16. Какие кадры становятся маршрутами.** В макете 163 кадра: 108 с верхней полосой (экраны), 17 помечены «компонент» или «фрагмент». Каждый экранный кадр — маршрут; компоненты и фрагменты — записи каталога; остальные (вход без оболочки, печать, окно настольного приложения, состояния) — список человеку на шаге 1 с предложением для каждого.
- **Р-17. Carrel.** Интерфейса в Carrel ещё нет, только спецификация, — переводить нечего. Интерфейс Carrel начинается сразу на 0.7.0 по руководству автора экрана: экран = кадр, собранный виджетами. Руководства по переходу и переходного слоя нет (Р-5).

## Шаг 1 — демо-экраны заново

- [ ] `internal/screens`: файл на раздел макета, функция на кадр, маршрут `/f/<data-frame>`. Тело функции — только виджеты и данные кадра, сверху вниз, как в `internal/proof/screens*.go`.
- [ ] Старые экраны удалить целиком: они собраны под старые ворота.
- [ ] Ворота `screens-coverage` → `frame-coverage`: у каждого кадра из списка Р-16 есть маршрут, у каждого маршрута есть кадр.
- [ ] `screens.css` — только оформление страницы демо (переключатель экранов, темы). Ворота `screens-css` остаются.
- [ ] Если кадр не собирается из виджетов — это пробел (шаг 5): кадр записать в `docs/visual/gaps.md` (кадр, чего не хватает) и перейти к следующему; обход на экране не делать. Пробелы закрываются по правилу шага 5 — макет, затем виджет, затем экран. Слияние ветки — только при пустом `gaps.md`.

## Шаг 2 — статическая сверка экрана с кадром

## Шаг 3 — сверка в браузере на лестнице ширин

Страница `/compare` пруфа становится тестом.

- [ ] `internal/browser/frames_test.go`: для каждого маршрута — кадр макета и экран на каждой ступени лестницы (`docs/visual/mockup.md`: 1351 / 1191 / 1190 / 1008 / 1007 / 820 / 641 / 640 / 460 / 390). Обход двух деревьев параллельно: прямоугольники узлов и текстовых кусков относительно корня кадра, вычисленные шрифт, цвет, фон, рамка, `display`, `position`, `white-space`. Допуск 0.5 px.
- [ ] Исключения — список в самом тесте, у каждого причина. Разрешено одно: внутренность `input[type=date|time]` (браузер рисует своё; коробка сравнивается). `allowed-diffs.md` сюда не относится: он про правки макета «до/после» в плане 1.
- [ ] Инварианты на каждой ступени: нет горизонтальной прокрутки страницы; соседи в потоке не перекрываются; лист и открытое меню сверху (`elementFromPoint` в их центре); текст не вылезает из коробки, кроме заданного многоточия; в состоянии `drawer` зона нажатия не меньше 44 px (Р-21; меряется зона, рисунок не растёт); страховка переполнения баров (Р-4) на содержимом кадров не срабатывает.
- [ ] Отдельный прогон с длинными подписями: в браузере, перед замером, текст кнопок в барах и шапке удваивается правкой DOM. Ожидание: страховка срабатывает, горизонтального переполнения нет.
- [ ] Уроки пруфа:
  - замеры синхронные, без `setTimeout` между шагами: в фоновой вкладке Chrome душит таймеры, прогон зависает;
  - макет и экран отдаются с одного сервера (иначе нет доступа к DOM кадра);
  - шрифты у обоих одни — макет рисуется шрифтами библиотеки.
- [ ] Укусы: сдвиг одного токена, одного правила, одного виджета в порядке — красное с путём до узла.

## Шаг 5 — руководство автора экрана

Короткий документ `docs/guide/screen.md`, ссылка из README и спеки.

- [ ] Экран начинается с кадра: найти `data-frame`; нет кадра — нет экрана.
- [ ] Перепиши кадр сверху вниз виджетами. Данные — из приложения; всё остальное — поля виджетов.
- [ ] Не собирается — это **пробел**, а не повод для обхода: сначала кадр или фрагмент в макете (по разделу «Как менять макет» `docs/visual/mockup.md`, со сверкой «до/после»), новая копия макета в Typecase, вырез CSS, потом виджет с эталоном (план 2), потом экран. На экране нет CSS, `style=`, классов `tc-*` руками.
- [ ] Проверка: `go test ./...` — статическая сверка; с Chrome — лестница ширин.
- [ ] Узкий вид не проектируется на экране: он уже в макете. Если на узкой ширине экран плох — правка в макете, на всех экранах сразу.
