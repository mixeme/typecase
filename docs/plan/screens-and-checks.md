Третий из трёх планов. Шаг 1 делается на ветке плана 2 ([library-from-mockup.md](library-from-mockup.md)) до её слияния; остальное — после. Первый план — [mockup-source.md](mockup-source.md).

**Цель.** Демо-экран — это кадр макета, собранный виджетами; браузер сверяет его с кадром на лестнице ширин, и красное значит «не как в макете», а не «число не совпало с таблицей». Недостающее сначала рисуется в макете. Carrel переходит на 0.6.0. Пруфы убраны.

## Почему так

Прошлые экраны демо собирались под ворота `screens-coverage` («каждый виджет каталога есть на каком-то экране»): дешевле всего было свалить виджеты раздела в одну колонку. Контакты несли десять кадров сразу, поиск 560×560 стоял посреди `main`, чипы и сегменты растягивались на всю колонку — при зелёных воротах. Look-тест мерил первый попавшийся узел каждого класса по списку чисел и этого не видел.

Здесь ворота устроены наоборот: маршрут = кадр, и сверяется весь кадр.

## Решения за человеком

Нумерация общая для трёх планов.

**Р-16. Какие кадры становятся маршрутами.** В макете 163 кадра: 108 с верхней полосой (экраны), 17 помечены «компонент» или «фрагмент». По умолчанию: каждый экранный кадр — маршрут; компоненты и фрагменты — записи каталога; остальные (вход без оболочки, печать, окно настольного приложения, состояния) — список человеку на шаге 1 с предложением для каждого.

**Р-17. Когда и как Carrel переходит.** По умолчанию: сразу после тега 0.6.0, отдельным планом в репозитории Carrel по тому же правилу — экран = кадр, собранный виджетами; копия макета в Carrel удаляется (Р-1).

## Шаг 1 — демо-экраны заново

- [ ] `internal/screens`: файл на раздел макета, функция на кадр, маршрут `/f/<data-frame>`. Тело функции — только виджеты и данные кадра, сверху вниз, как в `internal/proof/screens*.go`.
- [ ] Старые экраны удалить целиком: они собраны под старые ворота.
- [ ] Ворота `screens-coverage` → `frame-coverage`: у каждого кадра из списка Р-16 есть маршрут, у каждого маршрута есть кадр.
- [ ] `screens.css` — только оформление страницы демо (переключатель экранов, темы). Ворота `screens-css` остаются.
- [ ] Если кадр не собирается из виджетов — это пробел (шаг 5): стоп, сначала макет и виджет, потом экран. Список пробелов — в отчёт шага, не обход на экране.

## Шаг 2 — статическая сверка экрана с кадром

- [ ] Тот же `internal/fragment` из плана 2, корень — весь кадр: дерево маршрута равно дереву кадра.
- [ ] Тест `TestFramesStatic` по всем маршрутам. Без Chrome, в обычном `go test`.
- [ ] Это ловит то, что не ловит сверка виджетов: какой виджет выбран и в каком порядке стоит.

## Шаг 3 — сверка в браузере на лестнице ширин

Страница `/compare` пруфа становится тестом.

- [ ] `internal/browser/frames_test.go`: для каждого маршрута — кадр макета и экран на ширинах 1351 / 1100 / 900 / 820 / 620 / 460 / 390. Обход двух деревьев параллельно: прямоугольники узлов и текстовых кусков относительно корня кадра, вычисленные шрифт, цвет, фон, рамка, `display`, `position`, `white-space`. Допуск 0.5 px. Исключения — только из `docs/visual/allowed-diffs.md` (поля даты и времени рисуют своё).
- [ ] Инварианты на каждой ширине: нет горизонтальной прокрутки страницы; соседи в потоке не перекрываются; лист и открытое меню сверху (`elementFromPoint` в их центре); текст не вылезает из коробки, кроме заданного многоточия; в узком режиме цели касания не меньше размера из макета.
- [ ] Уроки пруфа:
  - замеры синхронные, без `setTimeout` между шагами: в фоновой вкладке Chrome душит таймеры, прогон зависает;
  - макет и экран отдаются с одного сервера (иначе нет доступа к DOM кадра);
  - шрифты у обоих одни — после плана 1 это так само.
- [ ] Укусы: сдвиг одного токена, одного правила, одного виджета в порядке — красное с путём до узла.

## Шаг 4 — каталог

- [ ] Запись каталога — фрагмент виджета из его эталона (план 2), по записи на состояние и вариант.
- [ ] Лестница ширин и переключатель темы в каталоге — как на странице макета.
- [ ] Компоненты и фрагменты макета (Р-16) — в каталоге рядом с виджетами, которыми собраны.

## Шаг 5 — руководство автора экрана

Короткий документ `docs/guide/screen.md`, ссылка из README и спеки.

- [ ] Экран начинается с кадра: найти `data-frame`; нет кадра — нет экрана.
- [ ] Перепиши кадр сверху вниз виджетами. Данные — из приложения; всё остальное — поля виджетов.
- [ ] Не собирается — это **пробел**, а не повод для обхода: сначала кадр или фрагмент в макете (по правилам плана 1, со сверкой «до/после»), потом виджет с эталоном (план 2), потом экран. На экране нет CSS, `style=`, классов `tc-*` руками.
- [ ] Проверка: `go test ./...` — статическая сверка; с Chrome — лестница ширин.
- [ ] Узкий вид не проектируется на экране: он уже в макете. Если на узкой ширине экран плох — правка в макете, на всех экранах сразу.

## Вне скоупа

- Правка виджетов — план 2; правка макета — план 1. Шаги этого плана находят пробелы и возвращают их туда.
- Новые экраны Carrel сверх нарисованного в макете.

## Готово когда

- Каждый кадр из списка Р-16 — маршрут демо, собранный только виджетами.
- Статическая сверка всех маршрутов зелёная; браузерная — зелёная на семи ширинах, исключения только записанные.
- Руководство автора экрана опубликовано, правило пробела в нём первое.
- Пруфов в модуле нет; Carrel на 0.6.0 или имеет план перехода.
